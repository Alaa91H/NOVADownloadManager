# تقرير الفحص وخطة الإصلاح والاستكمال — NOVA Download Manager

**تاريخ الفحص:** 16 أغسطس 2026  
**النطاق:** واجهة Tauri/React، إضافة المتصفح MV3، محرك Rust المحلي، بوابات الجودة، وسجل CI.  
**المرجع المحلي:** `main` عند الالتزام `fd171ce` وقت الاستنساخ.  
**حالة الوثيقة:** خطة تنفيذ حية؛ لا تُعامل كإثبات نجاح ما لم تُرفق بها نتائج بوابة التحقق في كل مرحلة.

> **قاعدة حاكمة:** لا يُدمج أي تغيير وظيفي أو أمني قبل وجود اختبار انحدار يثبت السلوك المطلوب، ثم مرور بوابات الجودة المتأثرة. لا تُسوّى الملاحظات الحرجة بالتوثيق وحده ولا تُغلق بسبب مرور فحص غير متعلق بها.

## 1. ملخص تنفيذي دقيق

المستودع متعدد المكونات: تطبيق سطح مكتب مبني على Tauri مع واجهة React/TypeScript، وdaemon مكتوب بـ Rust، وإضافة متصفح Manifest V3. توجد بنية اختبارات واسعة للواجهة والإضافة، كما توجد إجراءات CI وفحوص أمنية وآليات تدقيق مخصصة. أظهر الفحص الأولي أن الواجهة والإضافة قابلتان للبناء والاختبار محليًا بعد معالجة عيبين منخفضي المخاطر في جودة التطوير، بينما تعذر التحقق التنفيذي من backend Rust بسبب توقف تنزيل فهرس الاعتمادات الخارجي دون تقدم؛ لذا لا يجوز الادعاء بأن daemon أو حزمة Tauri اجتازا الاختبارات في هذه الجولة.

| المحور | النتيجة المؤكدة | الحكم الحالي | الأثر |
|---|---|---|---|
| تثبيت JavaScript | `pnpm install --frozen-lockfile` نجح في Node 24.19.0 | سليم محليًا | يمنع اختلاف الاعتمادات عن ملف القفل |
| واجهة React | `tsc` وESLint وPrettier و29 ملف اختبار/458 اختبار نجحت | أخضر محليًا | الثقة جيدة في المسارات المغطاة فقط |
| إضافة المتصفح | typecheck وESLint و69 ملف اختبار/745 اختبار نجحت | أخضر محليًا | ثقة جيدة في الوحدات والعقود المغطاة |
| بناء الواجهة والإضافة | `vite build` وWXT Chrome build نجحا | أخضر محليًا | لا يثبت تشغيل Tauri أو المتصفحات الحقيقية |
| Rust / Tauri daemon | سلسلة Rust والنظام ثُبِّتا، لكن `cargo fetch` بقي عالقًا في تحديث `crates.io` | غير محسوم | لا توجد نتيجة صحيحة لـ `check` أو `test` أو `clippy` أو `fmt` |
| توثيق التدقيق | تضارب بين `AUDIT_REPORT.md` الذي يعلن الإغلاق و`REPAIR_PLAN.md` الذي يسجل بنودًا مفتوحة | يحتاج تصحيحًا | خطر أن تُبنى الأولويات على حالة تاريخية غير دقيقة |
| التغطية الأمامية | إجمالي قياس التغطية 25.55% statements و18.93% branches | خطر جودة متوسط | العتبات الحالية تمرر تغطية منخفضة للواجهة الكلية |

## 2. التغييرات المنفذة في هذه الجولة

أزيلت عراقيل جودة مؤكدة دون تغيير سلوك المنتج. أولًا، كانت بوابة Prettier تفشل في أربعة ملفات من الواجهة؛ نُسّقت الملفات وفق إعداد المشروع. ثانيًا، أزيل استخدام `__dirname` من `vitest.config.ts` واستُبدل بـ `import.meta.dirname` المتوافق مع نمط ESM، ما أزال تحذير Vite الخاص بمحمّل الإعداد المستقبلي. ثالثًا، كان اختبار حالة «الجسر غير متصل» في الإضافة يطبع تحذيرًا متوقعًا إلى stdout؛ صار الاختبار يعترض التحذير ويثبت استدعاءه، فيحافظ على التحقق التشغيلي من دون تلويث سجل CI.

| المعرف | الملف/الملفات | السبب الجذري | المعالجة | تحقق ما بعد المعالجة |
|---|---|---|---|---|
| QL-001 | أربعة ملفات تحت `src/` | انحراف عن أسلوب Prettier المفروض | تطبيق التنسيق المعياري فقط | `pnpm run ci:format` أخضر |
| QL-002 | `vitest.config.ts` | استعمال `__dirname` في إعداد ESM؛ تحذير توافق Vite 8 | `import.meta.dirname` لمسار alias | اختبارات الواجهة تعمل بلا التحذير |
| QL-003 | `browser-extension/src/tests/unit/download-interceptor.test.ts` | خطأ Offline مقصود يطبع تحذيرًا غير مُلتقط | اعتراض `console.warn` والتحقق من الرسالة والخطأ | 745 اختبار إضافة تمر وسجل الاختبارات نظيف |
| QL-004 | `scripts/verify-branding-assets.mjs` | مدقق أصول العلامة كان يعد صور HTML coverage المؤقتة أصولًا غير مُدارة | استثناء بادئة `coverage/` من مسح أصول المصدر | `pnpm run audit:final` ينجح بعد توليد coverage |

## 3. سجل التحقق القابل لإعادة الإنتاج

كل أمر أدناه شُغّل من جذر المستودع في 16 أغسطس 2026. كلمة «نجح» تعني كود خروج صفري في هذه البيئة فقط، ولا تعني صلاحية النشر لمنصات Windows أو macOS ما لم تُنفّذ البوابات المكافئة عليها.

| الأمر | النتيجة | الدليل الكمي | الملاحظة |
|---|---|---|---|
| `pnpm install --frozen-lockfile` | نجح | lockfile مرّ بسياسة سلسلة التوريد | يتطلب Node `>=24` |
| `pnpm run ci:lint` | نجح | TypeScript وESLint بلا تحذيرات | بعد QL-001 وQL-002 |
| `pnpm run ci:format` | نجح | كل ملفات `src` مطابقة لـ Prettier | نطاق الأمر لا يغطي الإضافة |
| `pnpm run test:coverage` | نجح | 29 ملفًا و458 اختبارًا | التغطية الكلية منخفضة رغم مرور العتبات |
| `pnpm --filter nova-browser-extension ci:quick` | نجح | 69 ملفًا و745 اختبارًا | يتضمن WXT type generation وESLint |
| `pnpm run build` | نجح | حزمة الواجهة بُنيت | ليس بديلًا عن Tauri build |
| `pnpm --filter nova-browser-extension build:chrome` | نجح | Chrome MV3 output بُني | لا يثبت قبول متجر Chrome |
| `cargo check/test/clippy/fmt` | لم يكتمل | `cargo fetch` توقف في فهرس الحزم | عائق بيئة/شبكة؛ يجب إعادة المحاولة في CI أو مع مرآة معتمدة |

## 5. التسلسل الذري للتنفيذ

### المرحلة A: تثبيت الحقيقة التقنية

1. أنشئ فرعًا مستقلًا لكل مجموعة تغييرات ولا تعدّل `main` مباشرة.
2. ثبّت نسخة Node من `.node-version` ونسخة Rust من `rust-toolchain` أو وثّق غيابها.
3. أعِد تنفيذ Cargo في بيئة CI أو mirror معتمد، مع حفظ stdout ونسخة `Cargo.lock` المستعملة.
4. افصل الملاحظات إلى: عيب مؤكد، تحسين، دين تقني، وعائق بيئة. لا تُسجل مشكلة إلا مع موضع كود أو اختبار فاشل قابل لإعادة الإنتاج.
5. حدّث وثيقة تدقيق واحدة فقط بالنتيجة ورابط الالتزام والاختبار.

### المرحلة B: بوابة الجودة الموحدة

1. أضف أمر جودة موحّد يوقف التنفيذ عند أول عيب ويطبع جدول نتائج واضحًا.
2. شغّل JavaScript lint/format/test/coverage وامتداد المتصفح typecheck/lint/test/build.
3. شغّل Rust check/test/clippy/fmt/audit عند اكتمال تنزيل الاعتمادات.
4. شغّل build Tauri لكل منصة مدعومة عبر CI، ثم اختبارات packaging.
5. اجعل الـ workflow يرفع السجلات وتقارير التغطية عند الفشل، لا عند النجاح فقط.

### المرحلة C: رفع الثقة في السلوك الحرج

1. ابدأ بحدود التنزيل والإيقاف والاستئناف واسترداد الفشل؛ هذه سلوكيات تؤثر مباشرة في بيانات المستخدم.
2. لكل عيب: أضف اختبارًا أحمر، أصلح أقل سطح ممكن، ثم اجعل الاختبار أخضر؛ لا تمزج refactor واسعًا مع إصلاح سلوك حرج.
3. اختبر المرايا وإعادة المحاولة والـ redirects والـ IPv6 والملفات مجهولة الحجم والتحقق من checksum ضد خادم محلي قابل للتحكم.
4. اختبر pairing والتوكن والقيود الشبكية من منظور رفض الطلبات، لا نجاح المسارات فقط.
5. حدّث التغطية هدفًا بعد كل مجموعة بحيث لا تؤدي زيادة الاختبارات إلى كسر البنية دون داعٍ.

### المرحلة D: الإغلاق والتحضير للإصدار

1. راجع `git diff --check` وتأكد من أن كل تغيير له سبب واختبار.
2. راجع القابلية للوصول في الواجهة ومسارات RTL واللغة العربية.
3. نفّذ matrix المنصات، وافحص artifact واحدًا مثبتًا فعليًا لكل منصة.
4. حدّث changelog وREADME وسجل التدقيق من نتائج حقيقية، وليس من نوايا الإصلاح.
5. افتح طلب دمج مستقلًا يتضمن خلاصة، المخاطر المتبقية، ومخرجات البوابة.

## 6. دورة متابعة منضبطة بدل حلقة غير منتهية

لا يمكن تشغيل حلقة لا تنتهي بصورة مسؤولة؛ ذلك قد يستهلك الموارد ويغيّر الشيفرة بلا مراجعة بشرية. البديل الصحيح هو دورة محددة ومتكررة عند كل PR أو إصدار:

1. **استكشاف:** تأكيد النطاق، الحالة الحالية، والـ diff السابق.
2. **قياس:** تشغيل بوابة الجودة وجمع دليل قابل لإعادة الإنتاج.
3. **تصنيف:** تحويل النتائج إلى P0/P1/P2 مع مالك ومعيار قبول.
4. **تنفيذ محدود:** إصلاح مجموعة صغيرة متماسكة مع اختبارات انحدار.
5. **تحقق مستقل:** lint، format، tests، build، وCI المنصاتي.
6. **توثيق وقرار:** تحديث السجل ثم دمج/رفض/تأجيل واضح.

> تنتهي كل دورة فقط عند قرار موثق. تبدأ دورة جديدة من حالة Git ونتيجة CI الأحدث، لا من افتراض أن العيوب القديمة ما زالت قائمة.

## 8. أوامر التحقق القياسية

```bash
# تثبيت مضبوط
pnpm install --frozen-lockfile

# واجهة التطبيق
pnpm run ci:lint
pnpm run ci:format
pnpm run test:coverage
pnpm run build

# إضافة المتصفح
pnpm --filter nova-browser-extension ci:quick
pnpm --filter nova-browser-extension build:chrome

# Rust / Tauri — بعد نجاح cargo fetch
cargo check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo fmt --check --manifest-path src-tauri/Cargo.toml
```

## 9. مخرجات هذه الجولة

التغييرات الحالية محدودة عمدًا: تنسيق أربعة ملفات واجهة، تحديث توافق إعداد Vitest، وضبط اختبار Offline في الإضافة. يجب نقلها إلى فرع إصلاح منفصل مع هذه الوثيقة، ثم تنفيذ P0-RUST-001 وP0-TRUTH-001 قبل وصف المشروع بأنه «مكتمل» أو «مغلق تدقيقيًا».
